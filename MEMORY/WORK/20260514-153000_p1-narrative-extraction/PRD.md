## Context

### 任务概述
开发P1-A05叙事提取引擎(E05)，将海量模拟日志转化为可读的叙事文本。

### 业务背景
用户研究显示"眼高手低执行困境"是核心痛点——木剑这样的创作者不是"编故事"而是"发现故事"。叙事提取让用户能从海量演化日志中筛选高光时刻。

### PRD原文要求
| 字段 | 内容 |
|------|------|
| 编号 | A05 |
| 需求 | 叙事提取引擎：将演化日志转化为叙事文本的基础管线 |
| 优先级 | P1 |
| 验收标准 | (1) 章节结构合理（起承转合可辨识）(2) 单章生成≤3分钟 (3) 叙事连贯性（用户主观评分≥3.5/5） |
| 所属模块 | A-双轨并行架构 |
| 估算工作量 | 6人周 |

### 技术现状
- 事件存储：EventStore（SQLite + JSONL），包含turn、actor、action、score等字段
- 事件查询：QueryEngine支持按turn、actor、action_type等查询
- 已有`get_highlight_events`方法获取高分事件（score≥3.0）
- LLM适配层已实现（DeepSeek/OpenAI/Mock三模式）

### 设计决策
- 使用事件序列重写为流畅叙事
- 章节结构：起（背景铺垫）→ 承（冲突发展）→ 转（高潮转折）→ 合（余韵收尾）
- 利用已有score字段筛选高质量事件

## Decisions

### D1: 叙事提取vs故事淘洗分离
E05（叙事提取）和E01-E03（故事淘洗）是两个独立模块：
- E05：单事件序列 → 单章叙事文本（"这个事件线怎么写成故事"）
- E01-E03：从海量事件中发现值得讲述的事件线（"哪些事件线值得讲"）

当前先实现E05叙事提取（作为A05），E01-E03后续迭代。

### D2: prompt设计原则
- 系统prompt：角色设定（文风冷峻白描）+ 章节结构要求
- 用户prompt：事件序列（带时间/人物/动作/评分）
- 约束：保留原始事件的核心信息，不虚构情节
